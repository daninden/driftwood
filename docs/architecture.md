# Architecture of Driftwood

Driftwood is small and lonely: one island, one castaway, atmosphere first (see `design.md`). The architecture has to keep it that way. Every part has one job, can be tested on its own, and knows as little as possible about the rest.

## Layers

```
core/     numbers and noise           no dependencies
world/    the island as data          uses core (and only the curve maths of three)
game/     rules and game state        uses core and world
render/   everything you see          uses core, world (read only) and three
main.js   wires it all together       the only place that knows every layer
heightWorker.js, parallelHeights.js   build the height grids in Web Workers for main (use core and world)
```

Rules:

- **Arrows point one way.** `world` does not know `game` or `render`. `game` does not know `render`. `render` reads the world and the player state but never changes them.
- **`world` and `game` are pure.** They touch neither the DOM nor WebGL, so they run in Node (the tests) and in Web Workers (the height grids, see Loading).
- **Everything follows from the seed.** The same number gives the same island, the same trees and the same colours. Every tile has its own generator (seed, tx, tz), so the order in which tiles are built does not matter.
- **Almost no interface.** There is deliberately no HUD, map or menu. What you see is the island. The marks on screen are the moon that shows how rested the castaway is (`render/restMark`), next to it the drop that shows how thirsty he is (`render/thirstMark`) and the half coconut that shows how hungry he is (`render/hungerMark`), both in `#needs` and the row of what he carries loose (`render/carryMark`), top left the line with his name and the day (`render/nameLines`), and on touch screens the thumb stick and (everywhere) the action button (`render/thumbStick`, `render/actionButton`); all in one ink colour that turns pale at night (`render/ink`). The one exception is the developer panel (`render/devPanel`), a faint line top right with version, name, fps, work time per frame and `idle`; it is a developer aid, visible for now, to be hidden later (`DEV_PANEL_VISIBLE`), and toggled with the backtick key.

## Modules

| Module | Job |
|---|---|
| `core/noise` | Seeded noise (`vnoise`, `fbm`), PRNG and tile hash. The formulas are frozen. |
| `core/math` | `ss` (smoothstep), `lerp`, colour mixing. |
| `core/view` | The isometric view as angles (turn and tilt, with the tilt limits) and the zoom limits and start (`ZOOM_START`, `ZOOM_MIN`, `ZOOM_MAX`, and `ZOOM_DEV_MAX` 25 with `zoomMax(devVisible)`): what "towards the camera" and "screen right" mean for a given view, and `clampView(v, max?)` (a saved pose made safe). Pure maths; the camera owns the current angles. |
| `core/slicer` | Time slicing: heavy work as a generator that pauses when the frame budget is spent. |
| `core/loading` | The loading bar as one number: each generation step owns a measured share, so the bar fills evenly and never moves backwards. `main` draws it in `#loader` (`index.html`). |
| `world/constants` | Dimensions: 720 × 720 area, 0.25 grid, 40-unit tiles, terrace heights. |
| `world/shape` | Island outline and scattered highlands; scale to terrace level L. |
| `world/terrain` | From L to height: terraces, rock walls and the natural passages. |
| `world/heightfield` | The height and level grids, and bilinear sampling. |
| `world/rivers` | Rivers (Dijkstra, smooth curve), waterfalls, 2 to 4 fords per river along the middle reach (`rv.fords`, `rv.fordAt(k)`, `FORD_DEPTH`), carving beds and banks (shallow where a river is narrow, `bedDepth`; the bed rises to `FORD_DEPTH` on a ford; past the mouth the carve fades out over `MOUTH_FADE` samples so the bed flattens into the sea floor). |
| `world/vegetation` | Per tile: trees, palms, rocks, bushes, root spots, and what can be gathered: driftwood and the coconuts under the palms (each with its own PRNG and an id per piece) (data only). |
| `world/occlusion` | Darker ground under crowns and in hollows. |
| `world/spots` | Finding places: the start spot, examples of each passage (for tests). |
| `world/world` | Builds everything from a seed and returns one read-only object with queries. |
| `game/movement` | Walking rules: walls block, passages let you climb, the sea blocks below the current sea level and river water blocks deeper than `WADE_MAX` (0.35, waist deep; you can always wade back out), sliding along walls; trunks, boulders and crags (from the tile data, cached per tile) block and you slide round them; `weariStride(needsSpeed)` (1 - `WEARY_STRIDE` 0.4 x (1 - the combined speed of tiredness, thirst and hunger)) gives the shorter stride that `game/game` multiplies with the carrying stride; `canStand` and `nearestStandable` find a spot he can be put on (restoring a save). |
| `game/input` | Keys and clicks/taps to a movement intent (a double tap runs; the tapped spot itself is marked, steering after it is not; a finger may wobble a little); clicking and tapping only walk. The action button (0.13): `Space`, or a finger or the mouse on `render/actionButton` through `input.actionStart/actionEnd(id)`, gives `takeAction()` = `'tap'` (released within `HOLD_MS`) or `'hold'` (held that long, once, while still down), `actionFill()` for the ring, `cancelAction()` for the press that woke him; `Z` to sleep and `F` to light the pile beside him stay as keys; a left click, tap, the button or a walking key wakes (not the view controls); mouse wheel, `+`/`-` and a two-finger pinch to zoom steps; `Q`/`E`, right-mouse drag and a two-finger twist to turn (the mouse also tilts). The thumb stick: pure `stickIntent` (thumb offset + radius + yaw -> island direction and run, dead zone 12 %, run past 85 %) and `input.stickStart/stickMove/stickEnd`, which feed `input.stick` (a direction that follows the current yaw, preferred by `moveIntent`) and `input.run`; a stick finger is not a tap or one of the two fingers, and wakes like a walking key. |
| `game/wood` | Gathering: driftwood still on the beach, what is carried (at most 3, each piece slows you by `CARRY_SLOW`, 12 %, and shortens his step by `CARRY_STRIDE`), piles (at most `PILE_MAX`, 12, pieces each and of one `kind`; laying down fills the nearest pile with room and starts the rest as a new pile `PILE_NEXT` away; a first pile goes `FRONT` (0.45) in front of him; a pile never goes in the water: both use one `spotAround` search (the facing direction first, then alternating left and right in steps of 30 degrees, dry by a `wetAt` callback from `game/game`, clear of other piles), and when no spot is dry `drop` returns false and he keeps the wood); finding the nearest piece or pile, taking, laying down; washing up new wood at high water (deterministic per high water, never more per tile than at the start), piles the flood takes; washed-up wood is wet and dries over a day (`dryness`); `game/movement` `stepPlayer` takes a `stride` so the walk phase advances faster per metre with a load; piles and pieces taken off to burn; branches (0.16, `game/branches`) are pieces too: `createWood(world, saved, branches)` adds the branches on the ground to `find`, `take(thing, total)` takes one off the ground, `kindOf` gives `'branch'`, a mixed load is laid down kind by kind, and `consume(pile, n)` takes pieces off a pile to build; a plain saveable state. |
| `game/fibre` | Coconuts under the palms, husked for a tuft of fibre (at most 3 carried, one used up per attempt to light a fire); palms drop new nuts after some days; a plain saveable state. |
| `game/habitats` | Where the animals live (0.17, pure): crab colonies per tile (`coloniesOfTile`: holes on gentle ground between 0.4 m below and 1 m above high water, 3 to 5 crabs each), fish groups (`fishOfTile`: shallow river water away from falls, facing upstream, the shallow lagoons inside the island, found as shallow sea water with land on most sides within 40 m, and from 0.17.3 groups in the open sea over a bed 0.55 to 3 m below high water, `SEA_FISH`, with a PRNG of their own) and bird cells of 64 m (`birdCell`: 2 to 4 circling birds over a shore point, with the direction to the nearest rocky shore). Each from a PRNG seeded by the seed and the tile or cell, worked out when first asked for and kept, from existing world data only, so nothing is added to the world's generation and the seed 1337 fixture is untouched (the same trick as `game/branches`). |
| `game/wildlife` | The behaviour of the animals (0.17, pure, atmosphere only, not saved): `createWildlife(world)` with `update(dt, { x, z, time, sea, wading, asleep })` driven by real time, his place, the time of day and the sea level, and `crabs()`, `fish()`, `birds()`, `jump()` as lists of what is within `ALIVE` (30 m); nothing further away is updated or listed. Crabs run sideways near their hole, flee to the nearest hole within `SCARE` (3 m), stay hidden 10 to 20 s counted only while he is more than `SAFE` (5 m) away, and more are out at low water. Fish dart when he wades within `DART` (2 m), come back after 8 to 16 s, and a fish jumps beyond the surf every 30 to 90 s. Birds: circling by day (arriving and leaving by the way to the rocky shore, none at night), a flock landing 10 to 20 m away every few minutes (`callFlock` for tests), flushed within `FLUSH` (4 m). `game.wildlife` is updated at the end of `game.update`. |
| `game/branches` | The branches under the broadleaf and rain forest trees (0.16, pure): `branchesOfTile(world, tile)` works them out from `tile.trees` with a PRNG per tree (seeded by its place, nothing drawn in the world generation, so the seed 1337 fixture is untouched), cached per tile; a branch is a log-like piece `{ id, x, y, z, len, a, rad, branch: true }` (0.8 to 1.2 m, always dry) with an id from `BRANCH_ID0` (2^24) that encodes tile and number (`piece(id)` reads a saved one back). `createBranches`: `groundBranches(tile)`, `near`, `take(b, total)`, regrowth `REGROW` 4 + up to `REGROW_SPREAD` 4 days (`update(total)`), `version`, plain state `{ taken: [[id, day]] }`. |
| `game/leanto` | The lean-to (0.16, pure): `siteFor(piles, pile)` (a pile of at least `NEED` 6 and a partner pile of the other kind with 6 within `NEAR` 2 m, and the middle between them), `createLeantos`: `list` of `{ id, x, z, heading, progress }`, `start`, `unfinished(x, z, reach)`, `shelter(x, z)` (a finished one within `SLEEP_R` 1 m), `flood(sea)`, state `{ list, nextId }`. `BUILD_TIME` 60 s, `BUILD_COST` two drill attempts of rest. |
| `game/fire` | Fires: an attempt to light a pile (catches or not, from the dryness and tiredness, fixed by the seed and the number of attempts), burning down to embers and going out (a branch burns `BRANCH_BURN`, half, as long as driftwood: `fuelOf(logs)`), feeding one piece at a time, the flood putting them out; torches taken out of a fire, carried or stuck in the ground, lighting a dry pile without fibre (`kindle`), burning out, put out by water; whether a fire warms a sleeper; the burnt places a fire leaves when it goes out (two days, `burnt`, taken by the flood, replaced by a new fire); a plain saveable state. |
| `game/thirst` | Thirst (pure): days since he drank, running on while he sleeps, never past two days; thirsty at one day (slower, down to 0.65 at the collapse, `speed`), very thirsty at a day and a half (rest runs out twice as fast, `drain`), `faint` at two days (he collapses; `revive` puts him back to a day and three quarters on waking); `fill` for the drop mark; a plain saveable state `{ days }`. |
| `game/hunger` | Hunger (pure, modelled on `game/thirst`): days since he ate, running on while he sleeps, never past four days (it just stops; no collapse of its own); hungry at two days (`speed` down to 0.75 at four days, `drillCost` 1.5: drilling a fire costs half as much rest again), starving at four days (`drain` 1.5: rest runs out one and a half times as fast); `eat` takes `NUT_FOOD` (4/3 day) off, not below 0; `fill` for the half coconut mark; a plain saveable state `{ days }`. `game/game` multiplies `hunger.speed()` into the walking load and `hunger.drain()` with `thirst.drain()` into the `drain` it gives `game/sleep` (both together: 3 times), and scales the rest of a drilled fire by `hunger.drillCost()`. Finishing the husking (`HUSK_TIME` 4 s) gives the tuft, `hunger.eat()` and `thirst.sip(NUT_DRINK)` (a quarter day), always. |
| `game/water` | Which water can be drunk (pure): `freshWater` (river water, `inRiver` with the river level above 0, so not the sea, the lagoons or the mouth) and `findWater` (the nearest within a radius). |
| `game/castaway` | The name and the days (pure): `cleanName` (trimmed, at most 20 characters, empty = the castaway), `shouldAsk` (only at a real first start: no test parameters, no save with a name), `dayNumber` (day 1 is the day the game started), and the texts `dayLine` (`Dave, day 3`) and `wakeLine` (`Dave wakes. Day 3.`). |
| `game/clock` | The time of day and the number of days: a 20-minute day, part of the game state. |
| `game/tide` | Ebb and flow (pure): the sea level from the time, two high waters a day, and which high water it is. |
| `game/sleep` | Being awake, tiredness, and sleeping: how fast game time runs (20× while asleep, eased), lying down and getting up, tiredness slowing him down to 0.6 at two days, falling asleep after two days (only on dry ground); he can only choose to sleep after `SLEEP_AFTER` (half a day) awake (`canLie()`, asked by `game/game` for the button and Z; collapsing does not ask); a cold sleep without a fire ends after three hours (`COLD_SLEEP`) and rests 40 % (`COLD_REST` speeds the rest of that sleep up; six hours under a lean-to, `SHELTER_SLEEP`; by a fire under one he rests `SHELTER_REST` 1.25 times as fast: the fifth argument `shelter` of `update`); hard work tires (`tire`); `update` also takes `{ drain, faint }` from game/thirst (rest runs out faster, or he collapses into sleep). |
| `save` (src) | Automatic save in `localStorage`, one per seed: pure serialise/parse+validate (format number; optional `view` clamped with `core/view` `clampView`, garbage dropped), when to save (`momentKey`, and `createViewSaver`: once, 1.5 s after the view stops changing), the address hash (`#seed-…`, `new`), the reset key and the storage with try/catch. See Saving. |
| `game/game` | Game state (the player, the clock, the wood, sleep, the fibre, the fires and thirst) and the per-frame update. A click or tap target is looked at once and only walks (to beside wood, a pile, a coconut, a fire or a torch in the ground: an `act` of kind `'stand'`). `game.action()` is the pure "what can be done here": `{ tap, hold }` from what he carries and what he stands beside (`REACH` 0.55 for wood, a coconut or a torch in the ground, `BESIDE` 1.2 from the edge for a pile or a fire, 0.8 for river water), used by `update` for a press of the button (`input.takeAction()`) and by `main` to draw the icon: tap kinds `feed`, `pickup`, `husk` (always offered for a coconut within reach; the tuft only when there is room, `fibre.husk`), `torch`, `drink`, `plant`, `lay` in that order of priority (hands first, then the nearest), hold kinds `build` (0.16: a half-built lean-to within 1.7 m, or beside a pile with a partner pile, see `game/leanto`; wins over lighting; walks to beside the spot, kneels `BUILD_TIME` as work kind `'build'` whose progress is written into the lean-to every frame, so walking off keeps it; the heading is `input.yaw`), `light` (a pile of at least 4 beside him, with fibre or a torch) and `sleep`. A full fire (`game/fire` `full`) is never fed. Drinking with wood or a torch lays it down or plants it first (`queued` drink) and then kneels `DRINK_TIME` (`work` kind `'drink'`). A hold or `F` walks to the pile's side and kneels to drill fire or kindle with the torch; thirst slows him, drains rest and collapses him (see game/thirst); kneeling work stops, and a queued action is dropped, when `wantsToMove(input)` is true (keys, the thumb stick, which is `null` at rest, or a target); sleeping and waking (the flood wakes the castaway when it reaches him); the clock runs (faster while asleep), the tide washes up wood at high water and takes covered piles, fires burn down. |

Why the type and not the chunk: three.js keys its programs on the parameters (the shadow map type is one), not on the chunk text, so a changed chunk with `needsUpdate` would reuse the old program. A material that is not in the scene at the switch (a cached one) keeps the old filter until it is rebuilt: harmless, the two look alike. |

## One frame

The loop runs at the screen's rate but `main` only runs a frame when `render/framePacer` says it is due: at most 30 a second on touch-only devices (`touchOnly` from `render/thumbStick`), none on a desktop, and at most 15 a second on every device once nothing has been happening for 3 s. Happening: the castaway moving, working, bending, lying down or asleep (the sped-up sleep keeps the normal rate), the camera still easing (`view.settling`), a key held, the stick, a walking target, the action button held (its ring fills), and any pointer, touch, key or wheel event (listened for on `window` in the capture phase, so the stick counts too; an event while idle also drops the schedule, so the next screen frame is drawn at once). Fire and torch flicker and the slow sun and tide do not count. The game's `dt` is the time since the last drawn frame, clamped to 0.05 s (0.1 s while idle, so the game clock does not run slow at 15 fps). `__driftwood.frames` counts the drawn frames.

```
input ──> view.zoomBy(input.takeZoom()), view.turn(input.takeTurn(dt))
  │          zoom and view angles are view settings, not game state
  │      input.yaw = view.yaw   so the keys walk relative to the screen
  │
  └─> game.update(input, dt) ──> sleep or wake (game/sleep: how fast game time runs), a press of the action button or a click target is looked at
                │                (game/wood, game/fibre, game/fire), kneeling work goes on, the player moves (game/movement),
                │                the clock runs, the tide (game/tide) washes up wood, fires burn down, the animals within 30 m move (game/wildlife)
                │
                ├─> { rest } ──> the moon mark (render/restMark)
                ├─> game.action(), input.actionFill() ──> the action button (render/actionButton)
                ├─> thirst.days, hunger.days ──> the drop and the half coconut (render/thirstMark, render/hungerMark)
                ├─> fibre.carried ──> the carry row (render/carryMark)
                ├─> real frame time ──> the dev panel (render/devPanel)
                └─> { distance, terrain, time, sea } ──> view.render(player, info, dt)
                                                ├ camera follows; sun or moon from the time (render/sky)
                                                ├ sea level and surf of the tide
                                                ├ driftwood when game.wood changed or dried a step (fresh wood fades in), coconuts; castaway with its load and fibre, footprints
                                                ├ crabs, fish and birds near him (render/wildlife; they do not keep the frame rate up when idle)
                                                ├ fires: flames, smoke, the fire light and the night glow; tally marks of piles and fires beside the castaway
                                                ├ streaming: at most ~9 ms building tiles
                                                ├ far tiles on/off
                                                ├ window in the vegetation round the castaway
                                                ├ mood of the current terrace
                                                └ draw
```

## Quality

`main` picks the start level with `pickStart` (`?quality=N` forces a level and stops adapting, for tests; otherwise the level remembered in `localStorage` key `driftwood-quality`, one per device, not per island; else 0) and passes `settingsFor(level, { touch })` to `createIslandView`. After the island has faded in a governor (`createGovernor`) is fed, every drawn frame, the real time since the previous frame and whether the pacer idles. It measures the interval, not the work time, because the work time leaves out the graphics card; on a touch device capped at 30 a healthy interval is 33 ms, still under the 37 ms limit. When it steps down, `main` calls `view.setQuality(settings)` (`stage.applyQuality`), shows `qN` in the dev panel and saves the level (not with the test parameters `?spawn`, `?time`, `?awake`). `__driftwood.quality` gives the level. `npm run smoke -- --quality=N` runs the smoke test with a forced level.

## Loading

Loading takes about 3 seconds on a 4-core laptop. The height grids are the heaviest part (8.3 million points): `main.js` has them built in Web Workers, one per spare core (`src/heightWorker.js` computes strips of rows with `world/heightfield` `fillRows`, `src/parallelHeights.js` hands out the strips and puts the grids together). The result is exactly what a build on the main thread gives (tested); if workers are not available, `main` falls back to that. Then `islandView` builds the water and only the far tiles around the start (the others follow while playing), and `view.prepare` builds the detailed tiles in view at the start, so the game never opens on the simple stand-in tiles. A detailed tile costs about 0.15 s: its ground colour is sampled every second pixel and blended in between, and its 21 000 brush strokes are painted straight into the pixel data (`paintStroke`) rather than through the canvas API. `main.js` lets the browser breathe between the steps and fills the loading bar from the step reports (`core/loading`). When the first frame is drawn, the loader fades out and the island fades in.

Nothing stutters while playing, because detailed tiles are built in slices of about 9 ms per frame and the remaining far tiles in slices of about 3 ms.

## Saving

Built in 0.6: one automatic save per island in the browser's `localStorage`, key `driftwood-save-<seed>`.

- **The world is never saved.** It follows from the seed. What is saved is `game.state()`, a plain object: the seed, the time and day, the player's position and heading, how long he has been awake and the sleep in progress, the wood (carried, piles, washed up, lost, the last high water that brought wood), the fibre and coconuts taken, the fires, burnt places, torches and attempts, thirst and hunger. Not saved: the view, footprints, kneeling work and a pending tap.
- **Restoring is `createGame(world, spawn, saved)`.** The options of `createGame` are the shape of `state()`, so each part (`createClock`, `createWood`, `createSleep`, `createFibre`, `createFire`) starts from its own saved state, and `state()` of the restored game gives back the same object (tested). A saved position he cannot stand on any more (the island changed: a river now deep, a new boulder) is moved to the nearest spot he can (`game/movement` `nearestStandable`: rings of 0.5 m steps up to 15 m, using the walking rules via `canStand`), else to the start spot.
- **`src/save.js`** is the browser glue next to `main`: pure `serialise`, `parseSave` (format number `v: 1`, same seed, shape checked; anything else gives `null`, a fresh start, never a crash), `momentKey`, `parseHash`, `withoutNew`, `isResetKey`, and `createSaveStore(seed)` with `load`, `save`, `clear`, each wrapped in try/catch so blocked storage just means no saving. A save with another format number is ignored (and overwritten by the next save); the number goes up when the format changes incompatibly.
- **When it saves** (`main`): every 10 s of play, when `momentKey` changes (a pile gets wood or loses it, a fire is lit or goes out, a torch is planted or taken up, he falls asleep or wakes), and on `visibilitychange` (hidden) and `pagehide`. With `?spawn`, `?time` or `?awake` (the test parameters) nothing is loaded or saved, and the name question is skipped.
- **The view (0.10):** the format stays `v: 1`. A save may carry an optional `view: { yaw, tilt, zoom }` (camera `pose`: the turn wrapped into 0..2π, the tilt and zoom the player's goals, not the eased values). `parseSave` makes it safe with `clampView` (tilt 25°..45°, zoom 5..25; the camera then clamps to 10 unless the dev panel is visible) and drops a malformed one while keeping the rest of the save. `main` calls `view.setPose` right after the island view is created, before `view.prepare` chooses the tiles, so the first frame is already in the saved pose; a new start, `#new`, an old save or the test parameters leave the default view (turned 45°, tilted 30°, zoom 7). It is saved with every save and, through `createViewSaver`, once 1.5 s after the view stopped changing.
- **Thirst and burnt places (0.11):** the format stays `v: 1`. A save may carry `thirst: { days }` and `fire.burnt: [{ id, x, z, left, n }]` (at most 64); both are optional, so older saves load as not thirsty with no burnt places, and a wrong type makes the save unusable like any other broken field.
- **Branches and lean-tos (0.16):** the format stays `v: 1`. A save may carry `branches: { taken: [[id, day]] }` (the branches taken from the ground and the day, for their regrowing; ids from `game/branches`) and `leantos: { list: [{ id, x, z, heading, progress }], nextId }` (finished and half built; at most 64). Branches in piles need no field: they are in `wood.piles` with kind `'branch'` and their ids (≥ 2^24; `game/wood` reads them back through `branches.piece`). Both new fields are optional, so older saves load with no branches taken and no lean-tos, and a wrong type makes the save unusable like any other broken field.
- **Hunger (0.15):** the format stays `v: 1`. A save may carry `hunger: { days }` (days since he ate, clamped to 0..4 by `game/hunger`), optional like `thirst`: older saves load as not hungry, and a wrong type makes the save unusable like any other broken field.
- **The name (0.9):** the format stays `v: 1`. The save may carry two optional fields beside `game.state()`, added by `main`: `name` (string up to 40 characters; the empty string is an answer, "the castaway") and `startDay` (whole number: the clock's day on which the game started, so day 1). Optional fields need no migration: a save from before 0.9 has neither, so it asks once (`shouldAsk`: no name) and counts days from day 0. A wrong type makes the save unusable like any other broken field. `main` asks while the island loads, waits for the answer before the island fades in, and saves nothing until it has one (a save without a name would count as an answer); starting over clears the save, so the question comes back. The smoke test answers it with an empty Enter.
- **The address:** `parseHash` reads `#seed-<n>` and `new`, joined with `&` (`#new`, `#seed-2024`, `#seed-2024&new`). With `new` the save is cleared at start-up and `new` is removed from the address (`history.replaceState`), so a refresh keeps the game. Shift + backtick clears the save and reloads (saving is switched off first, so `pagehide` does not write it again). Plain backtick still toggles the dev panel.
- **A backend later** would sit behind the same `load`/`save`/`clear`, without `game` or `render` noticing.
