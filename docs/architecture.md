# Architecture of Driftwood

Driftwood is small and lonely: one island, one castaway, atmosphere first (see `design.md`). The architecture has to keep it that way. Every part has one job, can be tested on its own, and knows as little as possible about the rest.

## Layers

```
core/     numbers and noise           no dependencies
world/    the island as data          uses core (and only the curve maths of three)
game/     rules and game state        uses core and world
render/   everything you see          uses core, world (read only) and three
main.js   wires it all together       the only place that knows every layer
heightWorker.js, parallelHeights.js   build the height grids in Web Workers for main (use core and world)
```

Rules:

- **Arrows point one way.** `world` does not know `game` or `render`. `game` does not know `render`. `render` reads the world and the player state but never changes them.
- **`world` and `game` are pure.** They touch neither the DOM nor WebGL, so they run in Node (the tests) and in Web Workers (the height grids, see Loading).
- **Everything follows from the seed.** The same number gives the same island, the same trees and the same colours. Every tile has its own generator (seed, tx, tz), so the order in which tiles are built does not matter.
- **Almost no interface.** There is deliberately no HUD, map or menu. What you see is the island. The marks on screen are the moon that shows how rested the castaway is (`render/restMark`), next to it the drop that shows how thirsty he is (`render/thirstMark`, in `#needs`, where the half coconut of hunger will join it) and the row of what he carries loose (`render/carryMark`), top left the line with his name and the day (`render/nameLines`), and on touch screens the thumb stick and (everywhere) the action button (`render/thumbStick`, `render/actionButton`); all in one ink colour that turns pale at night (`render/ink`). The one exception is the developer panel (`render/devPanel`), a faint line top right with version, name, fps, work time per frame and `idle`; it is a developer aid, visible for now, to be hidden later (`DEV_PANEL_VISIBLE`), and toggled with the backtick key.

## One frame

The loop runs at the screen's rate but `main` only runs a frame when `render/framePacer` says it is due: at most 30 a second on touch-only devices (`touchOnly` from `render/thumbStick`), none on a desktop, and at most 15 a second on every device once nothing has been happening for 3 s. Happening: the castaway moving, working, bending, lying down or asleep (the sped-up sleep keeps the normal rate), the camera still easing (`view.settling`), a key held, the stick, a walking target, the action button held (its ring fills), and any pointer, touch, key or wheel event (listened for on `window` in the capture phase, so the stick counts too; an event while idle also drops the schedule, so the next screen frame is drawn at once). Fire and torch flicker and the slow sun and tide do not count. The game's `dt` is the time since the last drawn frame, clamped to 0.05 s (0.1 s while idle, so the game clock does not run slow at 15 fps). `__driftwood.frames` counts the drawn frames.

```
input ──> view.zoomBy(input.takeZoom()), view.turn(input.takeTurn(dt))
  │          zoom and view angles are view settings, not game state
  │      input.yaw = view.yaw   so the keys walk relative to the screen
  │
  └─> game.update(input, dt) ──> sleep or wake (game/sleep: how fast game time runs), a press of the action button or a click target is looked at
                │                (game/wood, game/fibre, game/fire), kneeling work goes on, the player moves (game/movement),
                │                the clock runs, the tide (game/tide) washes up wood, fires burn down
                │
                ├─> { rest } ──> the moon mark (render/restMark)
                ├─> game.action(), input.actionFill() ──> the action button (render/actionButton)
                ├─> fibre.carried ──> the carry row (render/carryMark)
                ├─> real frame time ──> the dev panel (render/devPanel)
                └─> { distance, terrain, time, sea } ──> view.render(player, info, dt)
                                                ├ camera follows; sun or moon from the time (render/sky)
                                                ├ sea level and surf of the tide
                                                ├ driftwood when game.wood changed or dried a step (fresh wood fades in), coconuts; castaway with its load and fibre, footprints
                                                ├ fires: flames, smoke, the fire light and the night glow; tally marks of piles and fires beside the castaway
                                                ├ streaming: at most ~9 ms building tiles
                                                ├ far tiles on/off
                                                ├ window in the vegetation round the castaway
                                                ├ mood of the current terrace
                                                └ draw
```

## Loading

Loading takes about 3 seconds on a 4-core laptop. The height grids are the heaviest part (8.3 million points): `main.js` has them built in Web Workers, one per spare core (`src/heightWorker.js` computes strips of rows with `world/heightfield` `fillRows`, `src/parallelHeights.js` hands out the strips and puts the grids together). The result is exactly what a build on the main thread gives (tested); if workers are not available, `main` falls back to that. Then `islandView` builds the water and only the far tiles around the start (the others follow while playing), and `view.prepare` builds the detailed tiles in view at the start, so the game never opens on the simple stand-in tiles. A detailed tile costs about 0.15 s: its ground colour is sampled every second pixel and blended in between, and its 21 000 brush strokes are painted straight into the pixel data (`paintStroke`) rather than through the canvas API. `main.js` lets the browser breathe between the steps and fills the loading bar from the step reports (`core/loading`). When the first frame is drawn, the loader fades out and the island fades in.

Nothing stutters while playing, because detailed tiles are built in slices of about 9 ms per frame and the remaining far tiles in slices of about 3 ms.

## Testing

```
npm test          unit tests (Vitest, Node), about 30 s
npm run build     builds dist/ and dist/driftwood.html (a single file)
npm run smoke     quick check (about 1.5 minutes): opens the build in headless Chromium at 640x400, answers the name question with an empty Enter, runs the whole story on game state (walks, gathers wood, low water, a cold sleep, a high water, husks a coconut, lights a fire, takes a torch, the action button by a pile and by the fire, held, and on a phone-sized touch screen with the thumb stick) and takes only a few screenshots: the loader, the start by day, the fire at night, tally marks, the action button by day and by the fire, and the phone
npm run smoke:full  the same with every screenshot (about 4 minutes); the shots a person looks at are 1280x800 (the phone at scale 2), the ones that only check something stay 640x400. Use it for visual versions
```

- `tests/world.test.js` compares seed 1337 with a golden file exported from the style prototype: heights, levels, slopes, rivers, passages, vegetation per tile and ground colours. Any change to the generation shows up here.
- `tests/movement.test.js` really walks over the island: every passage must lead up, walls without a passage must stop you, and so must the sea; trunks, palms and boulders must stop you while you slide past them, small stones must not; rivers stop you at waist depth, every ford can be crossed, the deep reach cannot, and upstream brooks can be waded anywhere.

Rendering itself is not checked by unit tests. That is what the smoke test with screenshots is for (`scripts/smoke.js`: quick by default, every shot with `--full`; the page is loaded once and the phone is a second page). Software drawing is slow and `toDataURL`/`readPixels` take seconds, so pixels are checked by `drawImage` of the canvas into a tiny 2D canvas in the page right after a draw (the start view by day must be brighter than the fire at night; no canvas may be blank). Shots the run skips still draw a frame, because tiles and tides depend on the frames drawn. A headless browser without a GPU draws only a few frames per second, so after loading the smoke test does not play in real time: it pauses drawing, runs the game in fixed 1/60 s steps and draws one settled frame per screenshot (`__driftwood.pause`, `step`, `draw` in `main.js`, for the smoke test only). Stepped walks leave no footprints, because those are laid while drawing.

## Publishing

The game is published on Vercel as a static site. The Vercel project is linked to the GitHub repository: every push to `main` is built there with `npm run build` and goes live from `dist/` (see `vercel.json`). So `main` is always what players see; run `npm test` (and for visual changes the smoke test) before pushing.

## Saving

Built in 0.6: one automatic save per island in the browser's `localStorage`, key `driftwood-save-<seed>`.

- **The world is never saved.** It follows from the seed. What is saved is `game.state()`, a plain object: the seed, the time and day, the player's position and heading, how long he has been awake and the sleep in progress, the wood (carried, piles, washed up, lost, the last high water that brought wood), the fibre and coconuts taken, the fires, burnt places, torches and attempts, and thirst. Not saved: the view, footprints, kneeling work and a pending tap.
- **Restoring is `createGame(world, spawn, saved)`.** The options of `createGame` are the shape of `state()`, so each part (`createClock`, `createWood`, `createSleep`, `createFibre`, `createFire`) starts from its own saved state, and `state()` of the restored game gives back the same object (tested). A saved position he cannot stand on any more (the island changed: a river now deep, a new boulder) is moved to the nearest spot he can (`game/movement` `nearestStandable`: rings of 0.5 m steps up to 15 m, using the walking rules via `canStand`), else to the start spot.
- **`src/save.js`** is the browser glue next to `main`: pure `serialise`, `parseSave` (format number `v: 1`, same seed, shape checked; anything else gives `null`, a fresh start, never a crash), `momentKey`, `parseHash`, `withoutNew`, `isResetKey`, and `createSaveStore(seed)` with `load`, `save`, `clear`, each wrapped in try/catch so blocked storage just means no saving. A save with another format number is ignored (and overwritten by the next save); the number goes up when the format changes incompatibly.
- **When it saves** (`main`): every 10 s of play, when `momentKey` changes (a pile gets wood or loses it, a fire is lit or goes out, a torch is planted or taken up, he falls asleep or wakes), and on `visibilitychange` (hidden) and `pagehide`. With `?spawn`, `?time` or `?awake` (the test parameters) nothing is loaded or saved, and the name question is skipped.
- **The view (0.10):** the format stays `v: 1`. A save may carry an optional `view: { yaw, tilt, zoom }` (camera `pose`: the turn wrapped into 0..2π, the tilt and zoom the player's goals, not the eased values). `parseSave` makes it safe with `clampView` (tilt 25°..45°, zoom 5..25; the camera then clamps to 10 unless the dev panel is visible) and drops a malformed one while keeping the rest of the save. `main` calls `view.setPose` right after the island view is created, before `view.prepare` chooses the tiles, so the first frame is already in the saved pose; a new start, `#new`, an old save or the test parameters leave the default view (turned 45°, tilted 30°, zoom 7). It is saved with every save and, through `createViewSaver`, once 1.5 s after the view stopped changing.
- **Thirst and burnt places (0.11):** the format stays `v: 1`. A save may carry `thirst: { days }` and `fire.burnt: [{ id, x, z, left, n }]` (at most 64); both are optional, so older saves load as not thirsty with no burnt places, and a wrong type makes the save unusable like any other broken field.
- **The name (0.9):** the format stays `v: 1`. The save may carry two optional fields beside `game.state()`, added by `main`: `name` (string up to 40 characters; the empty string is an answer, "the castaway") and `startDay` (whole number: the clock's day on which the game started, so day 1). Optional fields need no migration: a save from before 0.9 has neither, so it asks once (`shouldAsk`: no name) and counts days from day 0. A wrong type makes the save unusable like any other broken field. `main` asks while the island loads, waits for the answer before the island fades in, and saves nothing until it has one (a save without a name would count as an answer); starting over clears the save, so the question comes back. The smoke test answers it with an empty Enter.
- **The address:** `parseHash` reads `#seed-<n>` and `new`, joined with `&` (`#new`, `#seed-2024`, `#seed-2024&new`). With `new` the save is cleared at start-up and `new` is removed from the address (`history.replaceState`), so a refresh keeps the game. Shift + backtick clears the save and reloads (saving is switched off first, so `pagehide` does not write it again). Plain backtick still toggles the dev panel.
- **A backend later** would sit behind the same `load`/`save`/`clear`, without `game` or `render` noticing.
